# whip/whep の find_header_value のヘッダ解釈を堅牢化する

- Priority: Medium
- Created: 2026-06-05
- Model: Opus 4.8
- Branch: feature/fix-whip-whep-find-header-value
- Polished: 2026-08-05

## pending の理由

whip/whep 関連の対応を保留するため

## 目的

WHIP / WHEP の `find_header_value`（C 版）は HTTP ヘッダから指定した名前のヘッダ値を
抽出する関数だが、堅牢性の問題がある: 折り返しヘッダ（obs-fold による継続行）を連結せず
継続行を独立した行として扱う、同名ヘッダが複数行ある場合に最初の 1 行しか返さない、
行末が `\n` のみ（`\r` なし）の場合は途中行の検出に失敗する。これらを整理し、
CRLF 区切りのヘッダを正しく扱えるようにして抽出を堅牢化する。

なお C++ 版（`whip.cpp` / `whep.cpp`）は `absl::StrSplit` + `regex_match` + `std::map`
による独自実装のため、本 issue の対象外とする。

## 優先度根拠

Medium。現状の実装でも一般的な `\r\n` 区切りの単純なヘッダは抽出できている。
obs-fold は RFC 7230 §3.2.4 で deprecated（RFC 9112 §5.2 で再規定）であり、実運用で
遭遇する確率は低い。ICE サーバ情報を運ぶ `Link` ヘッダの抽出に使われるが、即時に
クラッシュする類のバグではないため High ではなく Medium とする。

## 現状

`whip_find_header_value`（`webrtc/src/whip.c`）と `whep_find_header_value`
（`webrtc/src/whep.c`）は完全に同一実装。

行末探索に `strstr(p, "\r\n")` を使用し `p = line_end + 2` で次行へ進んでいる。
行区切りは CRLF を前提としているが、以下の脆弱性がある:

- 折り返しヘッダ（継続行）を連結しない。継続行は独立した行として処理され、コロンを
  含まないため常に不一致でスキップされる
- 最初に一致した行で即 `return` し、同名ヘッダ複数行に対応しない
- 行末の扱いの不正確さ: `strstr(p, "\r\n")` が NULL になるのは「現在位置以降に `\r\n` が
  1 つも無い」場合に限られる。完全な LF-only 入力では全末尾を最終行と誤認し、混合改行
  （途中行が `\n` のみで後続に `\r\n` がある）では複数行が 1 行に結合された値が返る。
  なお実経路では、呼び出し元が `strstr(resp, "\r\n\r\n")` でヘッダ終端を検出してから
  本関数に渡すため、完全 LF-only のレスポンスはヘッダ終端検出で弾かれて本関数に到達
  しない。本関数で検証できるのは完全 LF-only（単体呼び出し時）と混合改行である。
  ヘッダ終端 `\r\n\r\n` の検出は本 issue の対象外とする

## 設計方針

- 行区切りは CRLF（`\r\n`）を基本とし、`\n` のみの行末も検出できるようにする。
  `strstr(p, "\r\n")` と `strchr(p, '\n')` の両方で行末を探し、先に現れる方を採用する。
  次行への前進量は CRLF なら 2 バイト、LF のみなら 1 バイトとする。単独の `\r`
  （CR のみの行末）は RFC 9112 では不正入力のため、行末としては扱わず値の一部として
  残す（対応しない）
- 折り返しヘッダ（継続行が空白 / タブで始まる行）は、直前のヘッダ値に連結して 1 つの
  値として扱う。連結時は継続行の先頭の空白 / タブを 1 つの SP に正規化する
  （RFC 7230 §3.2.4 の「replace each received obs-fold with one or more SP octets」に従う）。
  各行の末尾の OWS は連結前にトリムする（`A: v1 \r\n  v2` は `v1 v2` となる）
- 同名ヘッダが複数行ある場合は、すべての値を連結して 1 つの値として返す。
  連結の区切りはカンマ + スペース（`, `）とする（RFC 9110 §5.2 の
  「concatenated in order, with each field line value separated by a comma」と §5.3 の
  「For consistency, use comma SP」に従う。この連結は list-based フィールドを想定した
  措置であり、`Content-Length` のような非リストフィールドの結合値を 0018 がそのまま
  使うことはない前提とする。`Link` ヘッダのエントリ分割は 0021 が行う前提）
- フィールド名と `:` の間に空白を許容しない（HTTP の規定どおり、現状のまま）
- ヘッダ名の比較は大文字小文字を無視する（現状どおり `strncasecmp`）
- 値の末尾の OWS はトリムする（RFC 9112 §5.1。先頭 OWS は現状どおりスキップ）
- ヘッダ先頭行が空白 / タブで始まる場合（連結先のヘッダが存在しない不正な obs-fold）は、
  その行を無視して次行へ進む
- メモリ確保失敗（`malloc` が NULL を返す）は「ヘッダなし」と区別できるようにする
  （呼び出し元は NULL を「ヘッダなし」と解釈するため、確保失敗時も NULL を返す現状の
  挙動では「No Link header」と誤診断される。確保失敗時は英語のエラーログを出力して
  NULL を返すことで、ログで検知できるようにする）
- `whip.c` / `whep.c` の両方に同じ修正を入れる

## 完了条件

- CRLF 区切りのヘッダから、指定した名前のヘッダ値を大文字小文字を無視して正しく抽出できる
- 折り返しヘッダ（継続行）を SP 正規化して連結した正しい値として抽出できる
- `\n` のみの行末を含むヘッダからもヘッダ値を抽出できる（完全 LF-only・混合改行の両方）
- 同名ヘッダが複数行ある場合に、すべての値を `, ` 区切りで連結して抽出できる
- 値の末尾 OWS がトリムされる
- フィールド名と `:` の間に空白がある行は不一致として無視される
- ヘッダ先頭行が空白 / タブ始まりの不正 obs-fold は無視される
- メモリ確保失敗時は英語のエラーログが出力され、NULL が返る
- `whip.c` と `whep.c` の双方で同じヘッダ解釈が行われる

## テスト戦略

`webrtc/` 配下の C/C++ サンプルには自動テスト基盤がないため、手動確認で行う。
`find_header_value` の入力となるヘッダ列は単体で構成できるため、`main` 関数内の
動作確認用テストコードで以下を検証する。検証は `whip.c` と `whep.c` の両方で行う。

- 通常の CRLF 区切り・大文字小文字の混在
- obs-fold 継続行の SP 正規化連結
- 完全 LF-only・混合改行（途中行が `\n` のみ）での行末検出
- 同名ヘッダ複数行の `, ` 連結
- 末尾 OWS のトリム
- フィールド名と `:` の間に空白がある行の不一致
- ヘッダ先頭行が空白 / タブ始まりの不正 obs-fold の無視
- メモリ確保失敗時のエラーログ出力と NULL 返却（`LD_PRELOAD` / `DYLD_INSERT_LIBRARIES`
  による `malloc` フックで再現する。フックはテスト対象コードの差し替えではなく
  C ライブラリへの故障注入であり、AGENTS.md の「モックやスタブは絶対に利用しないこと」
  に該当しない）
