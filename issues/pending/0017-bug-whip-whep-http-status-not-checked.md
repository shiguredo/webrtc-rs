# whip/whep で HTTP ステータスコードを検証する

- Priority: High
- Created: 2026-06-05
- Model: Opus 4.8
- Branch: feature/fix-whip-whep-http-status-not-checked
- Polished: 2026-08-05

## pending の理由

whip/whep 関連の対応を保留するため

## 目的

WHIP / WHEP のシグナリングで、サーバから返ってきた HTTP レスポンスのステータスコードを
一切検証していない。WHIP 仕様（RFC 9725 §4.2）では POST に対して `201 Created` を、
WHEP 仕様（draft-ietf-wish-whep §4.3.1）でも POST に対して `201 Created` を期待するが、
現在の実装は `4xx` / `5xx` などの失敗レスポンスであってもボディを SDP として処理し続ける。
これによりエラーボディを SDP や Link ヘッダとして誤解釈し、誤動作や無言の失敗を招く。
レスポンスのステータスコードを検証し、期待した成功ステータス以外はエラーとして扱う。

## 優先度根拠

High 。サーバ側が認証エラー・レート制限・内部エラーなどで非成功ステータスを返した場合に、
エラーを検知できず誤った SDP 解析へ進む。失敗が無言のまま進行して原因究明が困難になる。
シグナリングの正しさに直結するため優先度を高くする。

## 現状

全 4 ファイルのレスポンス処理が、`\r\n\r\n` によるヘッダ終端検出のみで
ステータスコードをパースしていない。

- `whip.c` の `whip_OnSendRequestResponse` — `strstr(resp, "\r\n\r\n")` でヘッダ終端を
  検出後、即座に Link ヘッダ抽出と SDP 処理へ進む
- `whep.c` の `whep_OnSendRequestResponse` — 同一構造。ヘッダ終端検出後、すぐにボディ解析へ
- `whip.cpp` の `SignalingWhip::Connect` 内の SendRequest コールバック —
  `resp->find("\r\n\r\n")` で分割後、`absl::StrSplit` でヘッダ行パースへ進むが
  ステータスラインは無視される（`([^:]+):...` の正規表現にマッチしないため）
- `whep.cpp` の `SignalingWhep::Connect` 内の SendRequest コールバック — 同上

いずれもステータスラインを解釈するコードは存在しない。

目的の記述について補足する。実際は 4xx / 5xx の大半は Link ヘッダを持たず、
`No Link header` として先に失敗するため、「ボディを SDP として処理し続ける」のは
エラーレスポンスが Link ヘッダを含む場合に限られる。バグの本質はステータスコードを
一切検証していないことにある。

## 設計方針

- レスポンスの先頭にあるステータスライン（`HTTP/1.1 <status-code>` または
  `HTTP/1.1 <status-code> <reason>`、reason phrase は省略可能）を最初の `\r\n` まで
  抽出し、3 桁の数値コードをパースする。パース時は 3 桁ちょうどであること
  （`2010` のように 3 桁を超える場合）と、コード直後が空白または行終端であることを
  検証し、不正ならエラー扱いとする
- ステータスラインが `HTTP/` で始まらない場合や、数値コードがパースできない場合は
  不正レスポンスとしてエラー扱いする
- `1xx` 暫定レスポンス（`100 Continue` / `103 Early Hints` 等）が先頭に来た場合は、
  本 issue ではエラー扱いとする（1xx を読み飛ばす暫定レスポンス処理は行わない）

期待する成功ステータスコード:

| プロトコル | メソッド | 期待ステータス |
|-----------|---------|-------------|
| WHIP | POST | `201 Created` |
| WHEP | POST | `201 Created` |

WHIP / WHEP とも POST の成功レスポンスは `201 Created` のみを許容する（RFC 9725 §4.2 /
draft-ietf-wish-whep §4.3.1。`2xx` 全体を許容すると `202 Accepted` や `204 No Content`
を誤って成功扱いするため、`201` に厳密一致させる）。期待ステータス以外のレスポンスは
エラーとして扱い、ボディを SDP として解釈しない。

- エラー時はステータスコードと reason phrase を含む英語のログを出力する
  （例: `"Unexpected HTTP status: 403 Forbidden"`）。ステータスラインが不正な場合は
  レスポンスの先頭部分をログに出力する
- 4 ファイルすべてに対応する

### スコープ外のステータス（将来対応）

- `307 Temporary Redirect`（RFC 9725 §4.5 / draft-ietf-wish-whep-04 §4.7 がクライアントの
  リダイレクト対応を SHALL 要求）: 現行実装はリダイレクト未対応のため、本 issue では
  エラー扱いとする。リダイレクト対応は別 issue の対象とする
- `409 Conflict` + `Retry-After`（draft-ietf-wish-whep-04 §4.3.9 の再試行フロー）:
  本 issue ではエラー扱いとする。指数バックオフ再試行は別 issue の対象とする
- `406 Not Acceptable` + SDP カウンターオファー（draft-ietf-wish-whep-04 §4.3.2）:
  サーバがクライアント offer を拒否してカウンターオファーを返す成功進行ケース。
  現行実装は PATCH によるカウンターオファー応答に未対応のため、本 issue ではエラー扱い
  とする。カウンターオファーフローへの対応は別 issue の対象とする

特に断りのない限り、WHEP の仕様参照は draft-ietf-wish-whep-04 を基準とする。

## 完了条件

- 非成功ステータス（`3xx` / `4xx` / `5xx`）のレスポンスを受け取った場合、SDP 解析へ
  進まずエラーを返し、状態が `CLOSED` に遷移する
- ステータスラインが不正なレスポンスもエラーとして扱われる
- WHIP / WHEP とも `201 Created` の場合のみボディ処理に進む（`2xx` でも `201` 以外は
  エラー扱い）
- 4 ファイルすべてで同じ検証が行われる

## テスト戦略

`webrtc/` 配下の C/C++ サンプルには自動テスト基盤がないため、手動確認で行う。
ステータスラインの抽出・数値パースは関数として切り出し、`main` 関数内の動作確認用
テストコードで `201` / `200` / `1xx` / `3xx`（`307`）/ `4xx` / `5xx` / 不正な
ステータスライン（`HTTP/` 非接頭辞・数値コード非パース・`2010` のような 3 桁超過）の
各ケースを検証する。結合確認は、期待ステータス以外を返す試験用の HTTP サーバを使い、
SDP 解析へ進まずエラー中断されることを確認する。状態が `CLOSED` に遷移することは
`SignalingWhip_WaitForConnect` / `SignalingWhep_WaitForConnect` の戻り値で確認する。
試験用サーバは実サーバとして位置づけ、レスポンスの差し替えを目的としたモック・スタブは
使わない（AGENTS.md の「モックやスタブは絶対に利用しないこと」に従う）。
